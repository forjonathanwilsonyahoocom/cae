## Purpose

Define the **Distillation Operator** as a deterministic, falsifiable transformation function. Its job is to take an unstructured conversation transcript (or multi-turn interaction) and extract **candidate repository artifacts**, applying an explicit decision procedure to determine what gets committed to the repository and what gets discarded.

Without this operator, transcript processing degenerates into "elaboration-only progress"—generating visually impressive schema and documentation without increasing the repository's functional or decision-making precision.

---

## Operator Definition

The Distillation Operator ($D$) maps a conversation transcript ($T$) and repository context ($C$) to a set of evaluated commits ($A_{eval}$):

$$D(T, C) \rightarrow A_{eval}$$

Where each candidate artifact $a \in A_{eval}$ is defined as the tuple:

$$a = \langle \text{path}, \text{claim}, \text{evidence}, \text{falsifier}, \text{decision}, \text{rationale} \rangle$$

*   **path**: Target file path in the repository structure.
*   **claim**: The core load-bearing thesis (must be falsifiable, not a description).
*   **evidence**: Ground-truth citations or observations extracted directly from $T$.
*   **falsifier**: The exact test or observation that would invalidate the claim.
*   **decision**: `COMMIT` | `DISCARD` | `HOLD`.
*   **rationale**: Explicit reason for the decision based on repo goals.

---

## The Reconstruction Fork: Style vs. Decision

Every candidate artifact generated by this operator must pass through an explicit diagnostic fork before receiving a `COMMIT` decision:

```text
               Candidate Artifact Extracted
                            │
                            ▼
          Is this claim falsifiable in practice?
           ┌────────────────┴────────────────┐
          YES                                NO
           │                                 │
           ▼                                 ▼
 Does it reconstruct a prior decision     DISCARD / HOLD
  or establish a new, testable rule?    (Flag as "Style Transfer /
   ┌───────┴───────┐                    Elaboration-Only")
  YES             NO
   │               │
   ▼               ▼
 COMMIT         DISCARD

```

1. **Style Continuation (Discard Path):** The artifact merely matches the tone, vocabulary, or conceptual aesthetic of the repo without changing how the system or maintainer makes choices.
2. **Decision Reconstruction (Commit Path):** The artifact recovers or establishes a specific, reproducible decision procedure that alters execution, evaluation, or governance.

---

## Distillation Procedure

1. **Extraction (Smallest Load-Bearing Claims):** Filter $T$ for statements that can be tested or executed. Ignore conversational pleasantries, open questions, and vague ideas without stopping conditions.
2. **Anti-Pattern Filtering:** Scan extracted claims against known repository anti-patterns (e.g., answering counterarguments with additional schema, unbudgeted retries, lack of stop tests).
3. **Artifact Generation:** Format qualifying claims into concrete Markdown files matching repository schema.
4. **Evaluation & Decision:** Execute the Keep/Discard criteria. Record decisions inline or in a sealed verdict run (`ground_truth_verdicts.json` / YAML frontmatter).

## Worked Mini-Example

Below is an operational trace of this distillation operator executed on a real transcript segment.

### Input

* **Transcript Snippet ($T$):** User and AI discuss moving from open-ended verification to a loop-based approach with an explicit stop test based on claim consequence rather than iteration count.
* **Repo Goal ($C$):** Implement legible, budgeted verification for computational attention engineering.

### Extraction & Evaluation

#### Candidate 1: `patterns/verification-loop.md`

* **Claim:** Verification is a 4-step loop (`claim` → `check` → `update` → `stop test`) where termination is governed by confidence meeting a consequence threshold, not by iteration count.
* **Evidence from Transcript:** "Most verification failures aren't 'no evidence was checked' — they're 'the loop stopped at the wrong point.'"
* **Falsifier:** An experiment showing that fixed-count verification (e.g., "always check 3 sources") produces fewer false positives/negatives than a consequence-based stop test across equal token budgets.
* **Fork Diagnostics:** Falsifiable? **Yes.** Changes decision mechanics? **Yes** (determines when to stop checking).
* **Decision:** `COMMIT`
* **Rationale:** Establishes a reusable, operational shape for stateful verification.

#### Candidate 2: `concepts/verification-philosophy.md`

* **Claim:** "Verification is a journey of understanding between human and model."
* **Evidence from Transcript:** Implicit in the collaborative tone.
* **Falsifier:** N/A (Non-falsifiable prose).
* **Fork Diagnostics:** Falsifiable? **No.**
* **Decision:** `DISCARD`
* **Rationale:** Style continuation / elaboration-only progress. Adds vocabulary without changing system behavior or stopping conditions.
